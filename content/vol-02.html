Volume 2 — Database Internals and Distributed Databases

Part I: Systems Foundations · ~22 printed pages · Companion to Volume 1 (Distributed Systems)

0. Scope and reading model

This volume covers the machinery underneath a database — storage engines, logging, MVCC, isolation, query planning — and then the distributed layer built on top of it: replication topologies, distributed transactions, sharding, and the modern distributed-SQL designs. The organizing idea throughout: a database is a carefully arranged set of trade-offs between write amplification, read amplification, and space amplification, wrapped in a concurrency-control protocol and a recovery protocol. Nearly every design decision in every engine can be located on those axes. "Architecture review questions" boxes collect the questions that expose weak designs and weak schema choices, phrased so they can be used verbatim in a design review.

1. Storage engines: B-trees and LSM-trees

1.1 The two lineages

Almost every serious storage engine descends from one of two structures. B+-trees (InnoDB, Postgres heap+B-tree indexes, SQL Server, Oracle) update pages in place: a balanced tree of fixed-size pages (commonly 8–16 KB), where reads walk root→leaf in 3–4 hops and writes modify the target page. LSM-trees (RocksDB, Cassandra, HBase, LevelDB, and therefore CockroachDB, TiDB, YugabyteDB, Kafka Streams state stores) never update in place: writes go to an in-memory memtable, which is flushed to immutable sorted files (SSTables); background compaction merges files and discards overwritten values.

Fig 1 — The two storage lineages. Every "why is this database fast/slow at X" question starts here.

1.2 The amplification triangle

Write amplificationRead amplificationSpace amplification
B+-treeModerate-high: a 100-byte row dirties a whole page; plus WAL, plus (InnoDB) doublewrite bufferLow and predictable: O(log n) page reads, excellent for point and range readsModerate: pages run ~70% full; fragmentation over time
LSM, leveled compactionHigh: each byte is rewritten once per level (~10× over the tree's life)Low-moderate: one sorted run per level + bloom filtersLow: overwritten data compacted away promptly
LSM, tiered/size-tieredLower: fewer rewritesHigher: many overlapping runs to checkHigher: duplicates live longer (can transiently double)

This triangle is why write-heavy event/metrics workloads gravitate to LSM engines, why read-latency-critical OLTP with modest write rates stays happy on B-trees, and why compaction tuning (leveled vs tiered vs hybrid) is the central operational knob of every LSM store. Compaction also explains the characteristic LSM pathology: compaction debt — sustained write bursts outrun background merging, read amplification climbs, then compaction competes with foreground traffic for disk bandwidth exactly when the system is busiest. Mature deployments rate-limit compaction, watch pending-compaction bytes as a first-class saturation signal, and treat "L0 file count rising" as an early-warning alert.

1.3 Secondary structure notes worth knowing

  • Clustered vs heap storage. InnoDB clusters rows by primary key (table is the PK B-tree; secondary indexes store the PK, so long PKs bloat every index, and random UUIDs as PKs scatter inserts across the tree). Postgres stores rows in an unordered heap with all indexes pointing at physical row locations — which is why non-HOT updates must touch every index on the table.
  • Bloom filters give LSM reads a fast "definitely not in this file" check (~1% false positives at ~10 bits/key). They do not help range scans — one reason range-heavy workloads size LSM levels differently.
  • Modern hybrids: Bw-trees (Hekaton lineage), fractal/Bε-trees (buffered writes inside a B-tree), and WiscKey-style key-value separation (keys in the LSM, large values in a log) each move along the amplification triangle rather than escaping it.

2. Durability: WAL, checkpoints, and what "committed" means

2.1 Write-ahead logging

The write-ahead log is the single most important structure in a database. Rule: the log record describing a change reaches durable storage before the change itself does, and a transaction is committed when its commit record is durably in the log — not when data pages are written. Data pages can then be flushed lazily; crash recovery replays the log (redo) and rolls back losers (undo). The canonical algorithm is ARIES: fuzzy checkpoints, physiological logging, log sequence numbers (LSNs) stamped on every page, and repeat-history-then-undo recovery. Three practical consequences:

  • Group commit amortizes the expensive fsync across concurrent transactions — the reason a database can commit tens of thousands of transactions per second on a disk that does only a few thousand fsyncs per second. Settings like Postgres commit_delay or MySQL binlog_group_commit_sync_delay tune this batching.
  • Durability is configurable, and quietly. Postgres synchronous_commit=off, MySQL innodb_flush_log_at_trx_commit=2, Redis appendfsync everysec, Kafka acks=1 — all trade a window of acknowledged-but-losable writes for latency. Disks and virtualized storage add their own volatile caches beneath the database's fsync. A durability claim is only as strong as the weakest layer's flush semantics.
  • Checkpoints bound recovery time. Infrequent checkpoints → long log replay after a crash; aggressive checkpoints → I/O spikes during operation (checkpoint "storms" were a classic Postgres tuning problem before spread checkpoints). Recovery-time objective is thus partly a checkpoint-cadence decision.

2.2 The log is also the integration surface

The WAL's second life: replication ships it (physical or logical), and change-data-capture systems (Debezium reading MySQL binlog / Postgres logical decoding) turn it into an event stream. "The database's log is the database" is the conceptual bridge between OLTP systems and streaming architecture (Volume 11): a table is a view over a change stream, and a change stream is derivable from a table. Systems that grasp this get exactly-once-ish pipelines via the outbox/CDC pattern; systems that don't do dual writes.

Architecture review questions: "What is the durability setting on every store in the write path, including the disk cache layer beneath it — and does the acknowledged-write-loss window match what the business believes?" · "What is the measured crash-recovery time at current WAL volume, and when was it last tested with a real kill?" · "Is anything reading table state and separately publishing events (dual write), where CDC on the log would be atomic?"

3. MVCC: reading without blocking

3.1 The idea

Multi-version concurrency control keeps multiple versions of each row so that readers never block writers and writers never block readers. Each transaction gets a snapshot — a consistent view as of its start (or per-statement) — defined by transaction IDs or timestamps; row versions carry visibility metadata; a version is visible if it was committed before the snapshot and not deleted before it. All mainstream engines are MVCC engines; they differ in where old versions live:

EngineOld versions live…Consequence
PostgreSQLIn the table heap itself (a new physical row per update; old row marked dead)Needs VACUUM to reclaim dead tuples and freeze transaction IDs; update-heavy tables bloat; index entries multiply unless the update is HOT (same page, no indexed column changed)
MySQL/InnoDB, OracleNewest version in place; prior versions reconstructed from undo logs/segmentsLong-running transactions pin undo history: purge lags, snapshot reconstruction slows (Oracle's classic "snapshot too old")
LSM-based distributed SQL (CockroachDB, TiDB, Yugabyte)As timestamped keys in the LSMGarbage collection is a compaction concern; MVCC timestamps double as the distributed-consistency mechanism
Fig 2 — MVCC version chains and snapshot visibility. Garbage collection can only reclaim versions older than the oldest active snapshot.
Recurring production pattern: an analytics query, an idle-in-transaction connection from a leaked application session, or a stuck replication slot holds a snapshot open for hours. Version cleanup stalls behind it (VACUUM can't reclaim / undo purge lags), tables and indexes bloat, plans degrade, and in Postgres's worst case transaction-ID wraparound pressure forces emergency autovacuum. The visible symptom ("database slow, disk growing") appears far from the cause (one old snapshot). Monitoring the age of the oldest transaction/snapshot is as fundamental as monitoring disk space.

4. Isolation levels: the anomaly catalogue

4.1 Levels defined by what they permit

Repeatable read (ANSI)——possiblevariespossible
Snapshot isolation (SI)——mostly —— (first-committer-wins)possible
Serializable—————

Key facts that the ANSI table above obscures:

  • Defaults are weak. Postgres, Oracle, and SQL Server default to read committed; MySQL/InnoDB defaults to repeatable read (implemented as snapshot reads plus gap locks for locking reads). Most applications therefore run with lost-update and write-skew exposure unless they add explicit locking or version checks.
  • "Repeatable read" is not one thing. Postgres's REPEATABLE READ is true snapshot isolation. InnoDB's is snapshot reads for plain SELECTs but current-read semantics for SELECT … FOR UPDATE/DML — a mix that surprises people porting code between them.
  • Write skew is the anomaly worth memorizing, because snapshot isolation permits it and it maps to real invariants: two transactions each read an overlapping predicate, each writes a different row, both commit, and a constraint spanning the rows breaks. Classic instances: two doctors both going off-call because each saw "≥2 on call"; double-booking; balance checks across two accounts. No single row was written twice, so first-committer-wins never fires.
Fig 3 — Write skew. Fixes: SERIALIZABLE, or materialize the conflict (lock a row both must write, e.g. SELECT … FOR UPDATE on the roster row, or a constraint the database can check).

4.2 How serializability is actually enforced

  • Two-phase locking (2PL): acquire shared/exclusive locks, hold to commit. Correct, and the historical default; costs blocking, deadlocks (detected and broken by aborting a victim), and read/write interference. Predicate/gap locks close phantoms.
  • Serializable Snapshot Isolation (SSI): run optimistically on snapshots, track read-write dependency edges, abort a transaction when a dangerous cycle pattern appears (Postgres SERIALIZABLE). Non-blocking reads, occasional spurious aborts — applications must retry serialization failures, a requirement often discovered in production rather than design.
  • Optimistic concurrency control (OCC): execute, then validate read/write sets at commit; retry on conflict. Wins under low contention; collapses under high contention (retry storms). FoundationDB and many internet-scale stores use OCC variants.
  • Deterministic execution (Calvin/FaunaDB lineage): globally order transactions first, then execute without further coordination — removes 2PC from the commit path at the cost of requiring known read/write sets up front.
Architecture review questions: "Which isolation level does each critical transaction actually run at — the configured default, not the assumed one?" · "For every invariant spanning more than one row (limits, uniqueness enforced in code, balance rules): what prevents write skew — serializable isolation, an explicit lock, or a database-checked constraint?" · "Does the data-access layer retry serialization failures and deadlock victims, with bounded attempts?" · "Any read-modify-write done as read-then-UPDATE without a version check is a lost update waiting for concurrency — where are they?"

5. Indexing and query optimization

5.1 Index mechanics that drive design decisions

  • Composite index order is a prefix rule. An index on (tenant_id, created_at, status) serves predicates on tenant_id, on tenant_id+created_at, and range-plus-prefix combinations — but not on status alone. The design heuristic: equality columns first, then the range column, then columns needed only for output.
  • Covering indexes (all needed columns in the index, via key columns or INCLUDE) let the engine skip the table entirely — often the single biggest win for hot read paths, paid for in write amplification and storage.
  • Every index is a tax on every write. An insert into a table with 8 secondary indexes performs 9 structure modifications; in Postgres, any update touching an indexed column defeats HOT and touches all indexes. Index sprawl is the slow-motion failure of maturing schemas; unused-index audits (e.g. pg_stat_user_indexes) belong in operational hygiene.
  • Selectivity decides usefulness. An index on a boolean or low-cardinality status column rarely helps alone (the optimizer will prefer a scan past ~5–10% selectivity) — but a partial index (WHERE status='pending') on the rare hot value can be spectacular.
  • Random UUID primary keys scatter inserts across the tree (cache-hostile, page splits, bloated secondary indexes in clustered engines). Time-ordered identifiers (UUIDv7, ULID, Snowflake IDs) restore locality while keeping distribution-friendly generation — at the cost of concentrating inserts on the rightmost pages, which range-sharded distributed stores then need to split around (§8).

5.2 The cost-based optimizer: powerful, statistical, and therefore fragile

A modern optimizer parses to a logical plan, enumerates physically equivalent plans (join orders, join algorithms, index choices), estimates each plan's cost from table statistics (row counts, histograms, distinct-value estimates), and executes the cheapest. Three join algorithms cover almost everything: nested loop (best when the outer side is small and the inner side has an index), hash join (build a hash table on the smaller side; the default for large unsorted joins), merge join (both sides sorted; shines when indexes provide order). The systemic weaknesses worth internalizing:

  • Estimates compound multiplicatively. Correlated predicates (city='Bentonville' AND state='AR') are assumed independent; each join multiplies estimation error; a 6-table join can be off by orders of magnitude, at which point plan choice is effectively random. Extended/multi-column statistics exist precisely for this.
  • Stale statistics after bulk loads are the classic morning-after incident: last night's load doubled a table, autoanalyze hasn't run, the optimizer still plans for the old size, and a nested loop executes 50 million times.
  • Parameter sensitivity ("parameter sniffing"): a plan cached for a common parameter value is catastrophic for a skewed one (tenant with 10 rows vs tenant with 100M). Mitigations: per-value plans, plan guides/hints, or recompiling hot statements.
  • Plan flips are a change-management category. A minor version upgrade, a statistics refresh, or crossing a size threshold can flip a stable plan to a bad one overnight. Mature operations pin or baseline plans for the top revenue-path queries and diff plans before/after upgrades — treating query plans as artifacts to manage, like dependencies.
Architecture review questions: "For the ten most critical queries: what is the plan, what keeps it stable, and what alerts if it flips?" · "Which predicates are correlated, and do extended statistics cover them?" · "What is the write cost of the index set — and which indexes have zero reads in the last 90 days?" · "Is pagination OFFSET-based (O(n) per page, drifts under writes) where keyset/seek pagination should be used?"

6. Distributed transactions

6.1 Two-phase commit: the protocol and its price

Fig 4 — 2PC. Atomic, but a blocking protocol with a single point of failure at the coordinator, two round trips, and lock hold time spanning both.

2PC's problems in practice: prepared-but-undecided participants hold locks indefinitely if the coordinator is lost (heuristic manual resolution is the escape hatch, and it breaks atomicity); latency couples to the slowest participant; and abort rates climb with participant count. Modern systems respond three ways: make the coordinator highly available (Spanner runs 2PC over Paxos groups, so "coordinator" is itself a replicated state machine — the blocking problem dissolves, the latency remains), avoid crossing shards (choose partition keys so the dominant transactions are single-shard), or replace the transaction with a saga.

6.2 Sagas: transactions decomposed, atomicity traded for availability

A saga is a sequence of local transactions, each with a compensating action; on failure, completed steps are compensated in reverse (reserve inventory → charge payment → create shipment; if payment fails, release the reservation). Two coordination styles: orchestration (a state machine drives steps — debuggable, one place to see progress; the mainstream choice at scale, via workflow engines such as Temporal or step-function services) and choreography (each service reacts to events — no central coordinator, but the workflow exists only implicitly, and reasoning about partial failure across six services becomes archaeology). The non-negotiables sagas impose: intermediate states are visible (another service can observe reserved-but-unpaid inventory — the design must make such states meaningful, e.g. reservations with TTLs, not hidden), compensations can themselves fail (need retries + idempotency + a dead-letter escalation path), and some steps are not compensatable (an email sent, a payment captured at certain processors) — those must be ordered last or designed as reversible business operations (refunds) rather than technical rollbacks.

6.3 Percolator-style commit: distributed transactions over a KV store

The other widely deployed lineage (Google Percolator; TiDB today): snapshot-isolated transactions built on a versioned KV store using per-row locks, a designated primary lock as the atomic commit point, and timestamps from a central oracle. Commit = write the primary's commit record; all secondaries then reference it. Readers finding a stale lock resolve it by checking the primary — the protocol is crash-recoverable by construction. Worth knowing because it demonstrates the general trick behind most modern distributed transactions: reduce multi-key atomicity to single-key atomicity plus indirection.

7. Distributed SQL: the modern synthesis

Spanner, CockroachDB, TiDB, and YugabyteDB share one architecture, worth holding as a template: data split into ranges/regions (~64–512 MB), each range a Raft/Paxos group replicated across zones; transactions layered as MVCC + 2PC over those replicated groups (so participant failure doesn't block — the group fails over); timestamps from TrueTime (Spanner), HLC (CockroachDB), or a timestamp oracle (TiDB); SQL planned atop the distributed KV layer. The costs are equally shared: every write pays quorum latency (cross-region topologies put the speed of light in the commit path — geo-partitioning and leaseholder placement exist to keep quorums near writers); hot ranges need automatic splitting (sequential keys again); and clock-uncertainty handling (commit-wait vs read-restarts) is the tax for consistency without perfectly synchronized clocks.

Architecture review questions: "Which transactions cross shard/range boundaries, at what percentage of traffic — and could the partition key make them single-shard?" · "For each saga: the compensation table (step → compensating action → what if it fails), the visibility of intermediate states, and the non-compensatable steps ordered last." · "In the multi-region topology: where are quorum members and leaseholders for each table, and what is the write latency from each region's users?"

8. Sharding relational systems in practice

Volume 1 covered partitioning theory (hash vs range, consistent hashing, hot keys); this section adds what changes when the thing being sharded is a relational database with an application already attached.

  • The shard key decision is the whole game. It must (a) appear in the dominant queries, (b) distribute load, and (c) keep the dominant transactions single-shard. Multi-tenant systems shard by tenant almost by default — then need a plan for the whale tenant that outgrows a shard (tenant-level split, or promotion to a dedicated shard).
  • Proxy-based sharding (Vitess lineage) keeps MySQL/Postgres underneath and puts routing, query rewriting, and resharding workflows in a middle tier. Cross-shard queries become scatter-gather with restrictions; global secondary indexes become lookup tables maintained (approximately atomically) by the proxy layer. Coprocessor-style alternatives (Citus) push the same ideas into a Postgres extension.
  • Resharding is a data-movement workflow, not a config change: copy the historical data, tail the source's change stream to catch up, verify checksums, hold a brief write fence, cut over routing, keep reverse replication for rollback. The same choreography — bulk copy + CDC catch-up + verified cutover — is also exactly how large zero-downtime migrations between databases are done, which is why it deserves rehearsal as a standing capability rather than a one-off heroic project.
  • What is silently given up: cross-shard foreign keys and uniqueness (application- or lookup-table-enforced now), cross-shard joins (denormalize, or move the query to the analytics stack), auto-increment IDs (replaced by time-ordered distributed IDs), and single-database transactions for any flow crossing shards (back to §6).

Two meta-rules encode most organizational wisdom on this subject. First: default to boring. A well-run Postgres/MySQL with replicas, a pooler (OLTP connection counts kill databases before data volume does), and disciplined schema management covers a remarkable fraction of workloads; specialized engines are justified by a measured workload property, not by a diagram's elegance. Second: one system of record per fact; everything else is a derived view. Caches, search indexes, warehouses, and feature stores should be rebuildable from the system of record plus its change stream — the moment two stores can each claim to be the truth, reconciliation debt begins.

10. Operating databases: the topics that decide production outcomes

  • Online schema change. Naive ALTER TABLE on a large hot table can lock or rewrite for hours. The safe patterns: instant/metadata-only DDL where the engine supports it; ghost-table tools (gh-ost, pt-osc) or logical-replication-based changes elsewhere; and the universal choreography for anything semantic — expand → dual-write/backfill → verify → contract — with each phase a separately deployable, separately revertible step. Adding a NOT NULL column with a default, adding an index, and changing a column type each have engine-specific traps worth a checklist.
  • Backups are a restore capability, not a cron job. The measures that matter: restore time at current data volume (measured, recently), point-in-time recovery window (base backup + WAL archive), and whether backups would survive the same failure as the primary (region, account, ransomware — hence offline/immutable copies). Untested backups are a rumor.
  • Replication lag as a product parameter. Async replica lag bounds how stale read-replica traffic can be and how much data a failover can lose (RPO). Semi-sync/quorum acking trades write latency for a smaller loss window. This is a business decision expressed in database configuration, and it should be written down as one.
  • Connection architecture. Per-connection overhead (Postgres: a process each) means microservice fleets exhaust databases with idle connections; poolers (PgBouncer class) in transaction mode are effectively mandatory at scale, with their own caveats (session state, prepared statements).
  • Capacity signals worth alerting on before user pain: oldest-snapshot age (§3), replication lag, checkpoint/compaction backlog, connection saturation, lock waits, plan flips on top queries, and — for LSM systems — L0 file count and pending compaction bytes.

11. Architecture review checklist — databases

  1. System of record: one per fact; every other copy derived and rebuildable via the change stream.
  2. Durability chain: commit setting → fsync → disk cache → replication ack, stated end-to-end, with the acknowledged-loss window the business signed.
  3. Isolation vs invariants: each multi-row invariant mapped to its enforcement (serializable / lock / constraint); read-modify-writes carry version checks; serialization failures retried.
  4. Snapshot hygiene: alerts on long-running transactions, idle-in-transaction sessions, stale replication slots.
  5. Plan stability: top queries have known plans, statistics coverage for correlated predicates, and flip detection.
  6. Index budget: every index justified by a read path; unused indexes audited; write amplification accounted.
  7. Shard key: dominant transactions single-shard; whale-key plan; resharding runbook exercised.
  8. Cross-shard flows: 2PC scope minimized; sagas have compensation tables and non-compensatable steps last.
  9. Schema change: expand/backfill/contract discipline; large-table DDL patterns chosen per engine.
  10. Restore reality: measured restore time, PITR window, failure-isolated backup copies, last successful restore drill dated.

13. Chapter summary — ten sentences to retain

  1. Every storage engine is a position on the write/read/space amplification triangle; B-trees pay at write time, LSMs at read-and-compaction time.
  2. Committed means "commit record durably in the WAL" — and durability is a configurable chain whose weakest link (often a disk cache or an async setting) defines the real loss window.
  3. The WAL is also the integration surface: CDC on the log replaces dual writes.
  4. MVCC means readers and writers don't block — and that one long-lived snapshot silently poisons cleanup system-wide.
  5. Defaults are weak: read committed / repeatable read permit lost updates and write skew, which map to real broken invariants, not textbook curiosities.
  6. Serializability comes from 2PL, SSI, or OCC — the latter two require applications that retry aborts.
  7. The optimizer is statistical: correlated predicates, stale statistics, and parameter skew make plan management an operational discipline, not a tuning afterthought.
  8. 2PC blocks on coordinator loss; modern systems replicate the coordinator (Spanner-class), avoid crossing shards, or decompose into sagas with real compensation design.
  9. Distributed SQL = ranges × Raft × MVCC × 2PC-over-groups, paying quorum latency and hot-range management for regional survivability.
  10. Boring first, one system of record per fact, and backups measured by restore drills — most database strategy is these three sentences enforced.
