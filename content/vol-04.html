0. Scope and mental model

This volume covers the substrate applications run on: container isolation, Kubernetes internals and failure modes, the compute spectrum, cloud storage classes, cloud networking, and multi-region architecture. Two organizing ideas carry the whole volume. First, the control-plane / data-plane split: the data plane does the work (serve requests, move packets, run containers); the control plane decides the configuration of that work (schedule pods, program routes, update membership). Well-designed infrastructure keeps data planes able to keep running on last-known-good state when the control plane is down — static stability — and the severity of most platform incidents is determined by whether that property holds. Second, everything is reconciliation: modern infrastructure is declarative — desired state in a store, controllers converging actual toward desired in a loop. Reconciliation absorbs transient failure beautifully and turns misconfiguration into a persistent, self-reasserting fault; understanding a platform means knowing its controllers, their inputs, and their failure behavior.

1. Containers: what they are made of

1.1 Namespaces + cgroups + layered filesystems

A container is not a lightweight VM; it is an ordinary Linux process (tree) wrapped in three kernel mechanisms: namespaces partition visibility (PID, network, mount, UTS, IPC, user namespaces — each gives the process its own view of that resource); cgroups partition consumption (CPU, memory, IO limits and accounting); and a layered union filesystem (OverlayFS over content-addressed image layers) provides the image model — shared read-only layers plus a per-container writable layer, which is why images with common bases are cheap to store and fast to start. The runtime stack: an OCI runtime (runc) does the namespace/cgroup setup; containerd/CRI-O manage lifecycle and images; Kubernetes talks to them via CRI. Sandboxed runtimes (gVisor's user-space kernel, Kata's micro-VMs, Firecracker under serverless platforms) exist because a shared kernel is a shared attack surface — the isolation ladder is process < container < sandboxed container < VM, and multi-tenant-untrusted workloads belong on the right end of it.

1.2 The two resource-limit behaviors everyone eventually debugs

  • CPU limits throttle; requests weight. CPU requests set proportional scheduler weight under contention; CPU limits enforce hard quota per period (default 100ms) — a multithreaded service with limit=1 core can burn its quota in the first 10ms of a period across 10 threads, then sleep 90ms: p99 latency spikes with low average CPU. Latency-sensitive services frequently run with requests set honestly and limits removed (or generous), accepting weighted sharing instead of throttling; the decision deserves to be a stated policy, not folklore.
  • Memory limits kill. Exceeding a memory limit invokes the cgroup OOM killer — the process dies, often the JVM/Go runtime having no chance to react. Runtime heap settings must fit inside the limit with headroom for off-heap (JVM metaspace, direct buffers; Go's GOMEMLIMIT exists for exactly this). "OOMKilled, exit 137" loops are a container-native failure signature worth recognizing on sight.

2.2 The reconciliation model, precisely

Every Kubernetes behavior is one pattern instantiated repeatedly: a controller watches objects, compares desired vs observed, and issues idempotent corrections — level-triggered (act on current state), not edge-triggered (act on events), so missed events are harmless: the next loop converges anyway. Deployments → ReplicaSets → Pods is a controller chain; Services/EndpointSlices are a controller output consumed by kube-proxy; operators extend the same pattern to databases and Kafka clusters via CRDs. Three consequences worth internalizing:

  • Self-healing and self-harming are the same mechanism. The system re-asserts desired state relentlessly — deleting a "bad" pod by hand achieves nothing (the controller recreates it), and a wrong desired state is a fault that reapplies itself until corrected at the source. Debugging is therefore always "which controller wrote this, from what input" — follow the ownerReferences chain up.
  • Convergence has ordering freedom. Reconciliation makes few promises about when or in what order things converge; workloads must tolerate, e.g., a pod starting before its Service/DNS is programmed (crash-loop-with-backoff on startup dependency checks is normal, not an error to "fix" with sleeps).
  • API server + etcd are the shared-fate core. Watch storms (many clients re-listing large resource sets), oversized objects, and high-churn CRDs degrade etcd → API latency → every controller lags → the whole platform feels broken. etcd wants small objects, isolated fast disks (Volume 1's consensus warning applies verbatim), and defended request quotas (API priority & fairness). Cluster size limits are really etcd + watch-fanout limits.

2.3 Scheduling, disruption, and autoscaling — the operational triad

  • Scheduling = filter (resource requests fit? nodeSelector/affinity/taints satisfied?) then score (spread, bin-packing, custom). It runs on requests, not usage — so systematically over-requested workloads strand capacity (paid, unschedulable, idle), and under-requested ones overcommit nodes into eviction pressure. Request honesty is a FinOps issue and a reliability issue simultaneously.
  • Disruption management: voluntary disruptions (drains, upgrades) respect PodDisruptionBudgets; involuntary ones (node loss, OOM) don't. Topology-spread constraints + PDBs + graceful termination (preStop, SIGTERM handling, terminationGracePeriod aligned with drain deadlines from Volume 3 §4.3) are the difference between "node upgrades are invisible" and "every patch Tuesday is a mini-incident."
  • Autoscaling layers: HPA scales replicas on metrics (needs headroom and stable signals; on CPU it interacts badly with throttling); VPA right-sizes requests (in-place resize maturing; historically disruptive); Cluster Autoscaler / Karpenter-class provisioners add nodes when pods are unschedulable (minutes-scale — too slow for spikes, which is what overprovisioned headroom or warm pools are for). The layers interact: HPA adding pods → unschedulable → node scale-up → capacity arrives after the spike. Autoscaling is a control system, and untuned control systems oscillate.
Architecture review questions: "Does the platform pass the static-stability test — control plane down for an hour: what actually breaks?" · "Which workloads have CPU limits, and has anyone looked at their throttling metrics next to p99?" · "What are etcd's object-count, object-size, and watch-fanout hot spots — and what protects the API server from a misbehaving client?" · "For a routine node drain: PDBs, spread constraints, and termination grace verified — what error rate does a drain actually produce?"

4. Cloud storage classes and their contracts

  • Block (EBS class): a network-attached virtual disk for one instance — the substrate for databases. The contract details that matter: IOPS/throughput are provisioned dimensions (and can be the hidden bottleneck long before CPU); volumes are zonal (an AZ failure strands them — cross-AZ failover needs replication at the database layer, not the disk layer); snapshots are incremental to object storage and are the backup primitive. Local NVMe ("instance store") is faster and ephemeral — fine for caches and scratch, fatal for data that must survive an instance stop.
  • Object (S3 class): HTTP GET/PUT of immutable blobs: 11-nines-durability by cross-AZ erasure coding, strong read-after-write consistency (as of 2020 in S3's case), effectively infinite throughput if the keyspace spreads (per-prefix request limits reward key design), no rename (copy+delete), no appends (multipart composition instead), and per-request pricing that makes many-small-objects an anti-pattern (compact, or batch). Lifecycle tiering (standard → infrequent → archive) is where storage FinOps lives. Object storage is the cloud's real shared filesystem and the backbone of every lakehouse (Volume 11).
  • File (EFS/Filestore class): POSIX-ish shared filesystems — the right tool for lift-and-shift and shared-content patterns, with latency and locking semantics that disappoint anyone treating them as local disks.
  • The durability vs availability distinction deserves precision: object stores rarely lose bytes (durability) but do have outages (availability) — and a region-level object-store incident is a shared-fate event for everything above it. Critical data's cross-region replication is a deliberate architecture decision with a cost line, not a default.

5. Cloud networking: the VPC model

  • The mental model: a VPC is a private address space partitioned into zonal subnets, with route tables deciding where traffic can go, an internet gateway for public egress/ingress, NAT gateways for private-subnet egress, and security groups (stateful, instance-attached) plus network ACLs (stateless, subnet-level) as the filtering layers. Cloud networking is software-defined: "the network" is a distributed control plane programming host-level virtual switches — which is why its failures look like state-propagation failures (a rule applied in one AZ but not yet another) rather than cable cuts.
  • Cross-AZ traffic is metered. Inter-AZ data transfer has a per-GB price, which quietly shapes architecture: zone-aware routing (prefer same-AZ backends), replica placement, and chatty east-west protocols all have a cost dimension. Cross-region and egress-to-internet are steeper still; data-transfer line items are among the most common FinOps surprises (Volume 17).
  • Private connectivity: VPC peering (non-transitive, address-space Tetris), transit gateways / hub-and-spoke (the scalable enterprise pattern), and PrivateLink-class endpoints (expose one service into another VPC without route-table merging — the least-privilege option for service-to-service across trust boundaries, including SaaS). IP address planning (non-overlapping CIDRs across hundreds of VPCs, plus on-prem ranges) is unglamorous and, done badly, becomes a multi-year constraint; IPAM discipline early is cheap insurance.
  • Known chokepoints with limits and pricing: NAT gateways (per-GB processing charges and connection-scaling limits — a favorite silent cost and a favorite silent bottleneck for high-egress fleets) and per-instance/per-ENI connection-tracking limits (Volume 3 §7's state-exhaustion family, cloud edition).

6. Multi-region architecture

6.1 The honest decision tree

Multi-region is bought for three distinct reasons that demand different designs: latency (serve users near them — often satisfied by CDN + edge for read-heavy products without any multi-region write story), survivability (tolerate a region failure — the DR conversation: RTO/RPO targets priced against architecture), and data residency (regulatory partitioning — really a sharding-by-jurisdiction problem). Conflating them produces designs that pay active-active costs for what is actually a DR requirement.

6.2 Cell-based architecture: blast-radius engineering

Fig 2 — Cell-based architecture: many identical, isolated full-stack instances behind a minimal router; the deployment unit, capacity unit, and failure unit become the same thing.

Cells complement (not replace) multi-AZ and multi-region: AZs protect against infrastructure failure; cells protect against correlated software failure — the bad deploy, the poison request, the corrupted cache — which infrastructure redundancy replicates faithfully to every zone. The costs: per-cell capacity headroom (N smaller stacks bin-pack worse than one big one), cell-migration tooling for rebalancing and whale tenants, and the discipline to keep the routing layer thin (every feature added to the global router recreates the shared fate cells exist to remove).

6.3 Failover discipline: what separates paper DR from real DR

  • Failover must not depend on the failing region — runbooks, tooling, DNS control, identity/SSO, secrets, and artifact registries all need existence outside the affected region; circular dependencies here are the classic discovered-during-the-incident flaw. (Control-plane dependencies count: if deployment tooling runs only in the primary region, the standby can't be changed during the event.)
  • Data is the decision. Failover of stateless tiers is trivial; the real questions are the async replication loss window (RPO — signed off by the business in writing), replica promotion mechanics (and fencing the old primary — Volume 1 §4.4 verbatim), and the failback plan (returning is often harder than leaving: reverse replication, divergence reconciliation).
  • Exercised or fictional: failover paths decay — permissions drift, capacity assumptions rot, runbooks reference decommissioned systems. Quarterly game days that actually shift production traffic (or a deliberate "exercise the standby monthly by serving from it" rotation) are the only known preservative. A DR plan's real RTO is the duration of its last successful drill, not the number in the document.

7. Infrastructure as code and immutable infrastructure

Two disciplines close the volume because they underwrite everything above. Declarative IaC (Terraform/OpenTofu-class, or K8s manifests + GitOps controllers): infrastructure defined in version-controlled code, reviewed like code, applied by pipelines — the plan/diff step before apply is the safety mechanism, drift detection is the audit, and "someone changed it in the console" becomes an incident category to engineer away. Immutable infrastructure: never patch in place — build a new image/artifact, roll it out, destroy the old (the pets→cattle shift). Together they make environments reproducible, rollbacks real (previous artifact, not undo-scripts), and configuration drift — historically the largest source of "works in staging" — structurally impossible rather than procedurally discouraged. The mature endpoint is the platform treating everything (nodes, clusters, even regions in cell-based designs) as replaceable-from-code within a bounded time, which quietly is also the strongest DR posture available.

8. Architecture review checklist — cloud & infrastructure

  1. Static stability: control plane down one hour — enumerated actual impact, tested, not asserted.
  2. Resource honesty: requests reflect usage (utilization vs requests reported per team); CPU-limit throttling examined next to p99; OOMKilled loops treated as design bugs.
  3. etcd/API health: object size/count discipline, watch fanout, priority & fairness protections, isolated fast disks.
  4. Disruption readiness: PDBs + spread + graceful termination verified by a measured routine-drain error rate.
  5. Compute economics: utilization crossover computed for serverless vs provisioned; bin-packing owned by someone.
  6. Storage contracts: zonal-volume failure story at the database layer; object-store key-spread and small-object hygiene; lifecycle tiering active.
  7. Network cost & limits: cross-AZ traffic shaping (zone-aware routing), NAT gateway cost/limits, conntrack headroom, CIDR/IPAM plan that survives 5 years.
  8. Multi-region honesty: which of latency/survivability/residency is being bought; RPO signed by the business; failover free of circular dependencies on the failing region.
  9. Blast radius: largest correlated-failure unit named (cell? region? global router? shared control plane?) and accepted explicitly.
  10. Drill dates: last real region-evacuation / standby-serving exercise, dated, with measured RTO.

10. Chapter summary — ten sentences to retain

  1. Control planes decide; data planes do — and good platforms keep data planes serving on last-known-good state when control planes fail.
  2. Everything is reconciliation: self-healing and self-reasserting misconfiguration are the same loop, so debugging means finding the controller and its input.
  3. A container is namespaces + cgroups + layered filesystems around an ordinary process; the isolation ladder runs process → container → sandbox → VM.
  4. CPU limits throttle (latency spikes at low average utilization); memory limits kill (exit 137); requests are the scheduling and cost currency, so their honesty is both reliability and FinOps.
  5. etcd and the API server are the platform's shared fate: small objects, fast isolated disks, defended quotas.
  6. Autoscalers are stacked control loops with minutes-scale actuators — headroom covers the gap, and untuned loops oscillate.
  7. Object storage is the cloud's real shared filesystem: durable, strongly consistent, throughput-by-key-design, priced per request and per tier.
  8. Cloud networks are software-defined state machines with metered links; cross-AZ/egress pricing and NAT/conntrack limits are architecture inputs, not billing trivia.
  9. Buy multi-region for a named reason — latency, survivability, or residency — and prefer home-region partitioning and cells over symmetric active-active everywhere.
  10. A DR plan's real RTO is the duration of its last successful drill.
